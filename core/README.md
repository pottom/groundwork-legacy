# core

The shared core of Groundwork. It holds what every module uses.

| File | Role |
|---|---|
| `groundwork.mjs` | the command and the package's bin: `npx @pottom/groundwork [--root DIR] [--port N] [--no-open]` (or `node core/groundwork.mjs ...` in this repo). It stops with a clear message under Node.js 20, then loads `commands.mjs`; it is kept free of newer syntax so an old Node gets that far |
| `commands.mjs` | picks the command: a module's id with a `cli` in its manifest as the first argument (`groundwork plan apply` runs `modules/plan/plan.mjs apply`), else `init` anywhere among the options (`init.mjs`), else the server (`start.mjs`). The project folder is `--root`, else `MINDMAP_DIR`, else the current folder, for both; a missing option value or an unknown argument stops it with exit code 2 |
| `init.mjs` | `groundwork init [--root DIR] [--yes]`: sets a project up for Claude Code from the module manifests' `claude` field: copies each skill to `.claude/skills/<skill>/` (which then mirrors the packaged folder; `{{groundwork}}` in its Markdown becomes `RUNNER`), adds each hook as `<RUNNER> <run>` to `.claude/settings.json` (keeping everything else there, and replacing an older or other form of the same hook) and `.groundwork/` to `.gitignore`. It lists the changes and asks `[y/N]`; it writes only after a yes (no answer, or closed input, is no; `--yes` is for scripts). Run again, it changes only what is missing or out of date. `planInit({ root, modules })` gives the changes and `write()` |
| `start.mjs` | `start({ root, port, open })`: starts the server for the project, prints the addresses and opens the start page in the browser (`--no-open` skips it) |
| `version.mjs` | `VERSION`: Groundwork's one version, read from `package.json`; the modules' manifests carry it and the shell shows it in the header. `RUNNER`: how a set-up project runs Groundwork, `npx -y --prefer-offline @pottom/groundwork@<VERSION>` (this exact version of our package; once in the npx cache, no registry lookup) |
| `cli-process.test-helper.mjs` | runs commands for the tests: `startCommand` (a server; stops its whole process tree), `runCommand` (to its end), `npm`, `npx`, `startNpx` |
| `server.mjs` | `startServer({ root, modules, port })`, async: resolves to `{ port, url, close() }` once listening (`port: 0` picks a free one) and rejects a module whose id is reserved (`api`, `shell`, `vendor`). The local server: the shell at `/`, `/api/modules`, each module's view under `/<id>/` and endpoints under `/api/<id>/`. It listens on `127.0.0.1` and, where the machine has one, on `::1` too (see below), and keeps idle connections open for 65 s |
| `shell/` | the shell and the shared look: `shell.mjs` renders the start page on the server (a two-tier header: a bar with the logo, the project's name, the live state of the update stream, the language, the theme (System · Light · Dark) and the version, then a tab per module built from the manifests' `icon`, `name` and `tagline`, the tools (`tool: true`, like Sketch) after a separator; the chosen module's view in a frame; `/?module=<id>` picks one, and the rest of the query goes on to its frame, so `/?module=plan&node=d-trace` shows `/plan/?node=d-trace`: a module's deep link; in the browser the tabs switch modules in place, with history, and each visited module keeps its frame, only hidden (`frames.mjs`: inert, laid out at full size), so a switch is instant and the module keeps its state; narrow windows get one row); `theme.css` is the design system: the `--gw-*` tokens and the `.gw-*` components, documented at its top (the contract modules build with), light or dark following the OS until the user picks Light or Dark; it imports the components from `controls.css` and `feedback.css` beside it (a page links `theme.css` only); `shell.css` lays out the shell page; `live.mjs` is the tab's one live connection: the shell opens it and relays it to every module frame, hidden ones too (`relayEvents`), a module calls `subscribe({ onHello, onChange })`, which opens its own stream only outside the shell, and the stream closes on `pagehide`; `i18n.mjs` is the UI translation (English by default, Hungarian too; the EN · HU control in the header switches the shell and every module frame, and the choice survives a reload), with the shell's own strings in `strings.mjs`; `theme.js` is the light/dark switch: a plain script every page (the shell and each module's) loads first in its `<head>`, so it paints in the chosen theme; the System · Light · Dark control in the header sets the choice, kept in localStorage (`groundwork:theme`; missing or blocked storage means System), shown as `<html data-theme>` and switched live in every module frame (storage event and postMessage); a module's code that draws its own colours follows `groundworkTheme.theme` and `groundworkTheme.onChange((theme) => …)`, documented at its top. Of these, only `theme.css`, `theme.js`, `controls.css`, `feedback.css`, `shell.css`, `live.mjs`, `frames.mjs`, `i18n.mjs` and `strings.mjs` are served at `/shell/`; `shell.mjs` runs in the server and is never sent to the browser |
| `events.mjs` | the live updates: `GET /api/events` is a Server-Sent Events stream. The core watches the project folder (`fs.watch`, recursive); each module's manifest `watch(path)` names the topic of a changed file (`plan.map`, `build.files`, `build.git`, ...), and a module can push one itself (`events.publish(topic)`, or `events.every(ms, fn)` to check something on an interval while a page listens: Build asks GitHub afresh every minute and pushes `build.issues`). `events.stamp()` lets a module keep what it read until a file changes: `null` while the folder is not watched, otherwise a string that stays the same exactly as long as no file below the root changed (Build keeps its project listing this way). A `change` event carries `{ topics }` only, never content: the page asks its endpoints again. Topics within 150 ms go out as one event. On connect the stream sends `retry: 2000` and a `hello` event; EventSource reconnects by itself, and the pages read everything again on each `hello`, so a change missed while disconnected is not lost. Plan and Build follow it instead of polling |
| `project-name.mjs` | `projectName(root)`: the project's name for the shell and the modules: the first heading of `README.md`, else `package.json`'s name without its scope, else the folder's name |
| `sse-client.test-helper.mjs` | a small SSE client for the tests (`listen(port)`) |
| `modules.mjs` | the list of modules the server loads, in the order of the shell's tabs (the flow: Ideas `/ideas/`, Plan `/plan/`, Build `/build/`; then the tools, behind a separator: Sketch `/sketch/`); the first is shown at `/` |
| `files.mjs` | the writer each module gets: reads inside the project, writes only under the folders its manifest names (`docs/product/` and `.groundwork/` at most) |
| `http.mjs` | small helpers for the server and the modules' endpoints: `send` (data: `no-store`, `nosniff`, `content-length`), `sendCached` and `sendFile` (pages and files: an `ETag`, `304` while unchanged, brotli or gzip when the browser accepts it), `readJson` |
| `vendor/` | the browser-side dependencies (Mind Elixir, marked, lit-html, the Inter and Source Serif 4 fonts; Excalidraw with React, loaded only by the Sketch page), served at `/vendor/...`; versions and licenses in [`vendor/README.md`](vendor/README.md) |
| `offline.test.mjs` | checks that no page loads anything from another host |
| `cli.test.mjs`, `init.test.mjs`, `package.test.mjs` | the command as a process (a project folder, the Node version check, `groundwork plan`, the bin's LF line ends), `groundwork init`, and the npm package: its file list, and the packed tarball served by a local test registry and used outside the repo as a user does: `npx -y @pottom/groundwork`, `npx -y @pottom/groundwork init`, then the installed hook and skill command, also with the registry gone |

The npm package (`package.json` `files`) holds `core/` and `modules/` without the tests and test helpers (`*.test.mjs` and `*.test-helper.mjs`, one pattern: `!**/*.test*.mjs`); `docs/`, `.claude/` and everything else stay out. `.gitattributes` keeps LF line ends on every OS, so a package packed on Windows still runs on macOS and Linux.

The server listens on the loopback only: `127.0.0.1`, and `::1` as well where the machine has an IPv6 loopback. `localhost`, the address it prints and opens, resolves to `::1` first; without a listener there every new connection waited for the browser's IPv4 fallback (about 200-300 ms). It answers a request with a foreign `Host` header with 403 (the event stream too); `localhost`, `127.0.0.1` and `[::1]` are its own.

Caching: data under `/api/` is never kept (`no-store`). The shell page, `/shell/`, `/vendor/` and the modules' view files are sent with an `ETag` and `no-cache`, so the browser asks each time and gets an empty `304` while the file is unchanged; fonts may be kept a week (`cachePolicy` in `http.mjs`). Nothing is kept for good: a checkout changes its files without a new version. Text of 1 KB or more is sent compressed (brotli, else gzip) when the browser accepts it, each file compressed once. It uses only Node's built-in modules, and every page loads its libraries and fonts from the server, so Groundwork works without a network.

A module plugs in with a manifest; see [`../modules/README.md`](../modules/README.md).

The module ids `api`, `shell` and `vendor` are reserved for the core's own paths; `startServer` rejects a module that uses one. The decisions behind the core are in [`docs/product/core/TECH.md`](../docs/product/core/TECH.md) (in Hungarian).
